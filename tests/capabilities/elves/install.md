Установка флоу: одна команда `bunx @miroshnik/elves install` ставит проекту флоу последнего релиза Elves для
Claude Code — тонким, без копии; с `-g` машина получает канон, скиллы и хук.

Проект тонкий (#552). Копия флоу в `.agents/` стоила дорого: обновление — отдельная задача и PR на тысячи строк (в
одном проекте 9 обновлений за 15 дней, до +5,8k/−2,7k строк за раз), плюс исключения в `.gitignore`, линтерах и
форматтерах. Теперь в репозитории — только версия пакета `@miroshnik/elves` в `devDependencies` (харнесс тестов,
spec-скрипты и CI проекта — его версии: `bun install` приносит её в CI и коллеге), манифест `.agents/elves.json`,
шим очереди `.agents/slot.sh` и блок в `AGENTS.md` со ссылкой на канон машины; канон и скиллы живут на машине.
Обновление проекта — подъём версии, несколько строк в ветке текущей задачи. Версия — точная, релиза, которым идёт
установка (тег `v2026.10.15.1` — `2026.1015.1`): это версия проекта, и `check` сравнивает её с релизом.
`install` пишет её в `package.json` и зовёт `install` менеджера пакетов проекта — тот обновляет свой lockfile; без
lockfile — только `package.json` и строка с командой: lockfile, которого проект не держит, установка не заводит.
Менеджер не смог (нет сети, песочница агента) — предупреждение с командой: `package.json` уже верный. Проект без
`package.json` версии не получает — закреплять нечего. Установщик из клона или пускатель из `main` без релизов — не
релиз: версию не знает, `devDependency` не трогает и говорит об этом (#558, вопросы 1 и 5). Отвергнуто: версия в
манифесте — её уже закрепляет `devDependencies`, по нему `bun install` и ставит пакет; `bun add`, `npm i -D` и
другие по менеджеру — четыре разные команды, а правка `package.json` и одна команда `install` — для всех.

Скрипты скиллов проект зовёт пакетом: `bun --no-env-file node_modules/.bin/elves <скрипт>`, в `package.json` и в CI
одинаково (#596): `bun` читает bin пакета сам, мимо шебанга, и без флага подгрузил бы ему env-файлы проекта, а скрипт
отдал бы их ключи `gh`, `git` и проверяемой команде (стандарт `no-env-file`; голый bin снимает их шебангом через `sh`,
#592); шаг GitHub Actions не видит `node_modules/.bin`, а `bunx elves` без пакета в node_modules скачал бы из npm чужой
пакет `elves` (#558, вопрос 2). Отвергнуто: bin, который перезапускает себя под `--no-env-file`, — окружение родителя
уже загружено, ключи файлов пришлось бы вычищать; шебанг `#!/usr/bin/env -S bun --no-env-file` — `env -S` есть не
везде (busybox).

На машине (#557) — канон: `~/.agents/elves/` и симлинки `~/.claude/rules/elves*.md`, скиллы в
`~/.agents/skills` и `~/.claude/skills`, хук. Тонкий проект (эпик #554) копии не держит, и канон его агент берёт с
машины. Для Claude Code годятся только правила `~/.claude/rules`: они грузятся без диалога внешних импортов и во всех
проектах машины, а `@~/`-импорт из CLAUDE.md проекта в сессиях приложения не грузится — одобрение нужно на каждый
worktree (#552). Флаг «правила на машину — по желанию» отвергнут: тонкий проект без канона машины остался бы без
правил.

Хуков в `~/.claude/settings.json` два: `SessionStart` — проверка флоу и окружение Bash агента — и `PreToolUse` (#839,
capability `github#github-guard`): обход команды флоу запрещён с её командой в причине. У `PreToolUse` — обработчик на
каждое правило списка обходов скилла `github`: `if` Claude Code берёт одно правило, и вызов без подходящей подкоманды
процесса не стоит. Команда — скрипт `github` машины по пути, а не `bunx`, как у `SessionStart`: хук идёт перед вызовом
и отвечает за десятки миллисекунд, без сети. Своим установка считает обработчик с командой `github.ts hook guard`:
набор прошлой версии `install -g` и `update -g` заменяют целиком, хуки пользователя остаются, `check -g` называет
отсутствующий или другой набор отставанием.

Эльфы — для Claude Code (#848, решение владельца, вопрос 2 эпика #833): за два месяца на машине нет ни одной сессии
других агентов, кроме четырёх сессий Codex, а хуки, пин сессии к задаче, факт из транскриптов, диспетчер с субагентами
и архивация сессии есть только у Claude Code. Поэтому `install -g` файлов правил других агентов не пишет — прежде
писал симлинк на канон в `~/.gemini/GEMINI.md`, `~/.copilot/copilot-instructions.md`, `~/.config/opencode/AGENTS.md`,
`~/.config/amp/AGENTS.md`, до #836 — и в `~/.codex/AGENTS.md`, и подсказку для Cursor. Машина прошлой версии их держит:
`install -g` и `update -g` убирают их, `check -g` до обновления называет отставанием. Своим установка считает только
симлинк в канон — так их писала прошлая версия; чужой файл или симлинк с правилами пользователя остаётся, каталог агента
— тоже: его установка не заводила. Другому агенту — короткая инструкция `docs/other-agents.md`: канон подключить
глобальными правилами агента, скиллы взять из `~/.agents/skills` — путь стандарта Agent Skills, поэтому скиллы на машине
остаются там со ссылками из `~/.claude/skills` (вопрос 1 задачи; на эти пути ссылаются и настройки песочницы и
разрешений владельца), блок в `AGENTS.md` проекта ведёт к канону любого агента, читающего файл проекта. README называет
только Claude Code и ссылается на инструкцию. Отвергнуто: держать файлы правил для агентов, которыми никто не
пользуется, — обещание поддержки без единой сессии, которой его проверить.

Команду `elves` в терминале `install -g` тоже ставит (#632): после установки работали только `bunx @miroshnik/elves …`
и `bun <клон>/bin/elves.ts …`, а глобальный пакет (`bun add -g`) кладёт бинарь в `~/.bun/bin`, которого в PATH часто
нет (Bun из Homebrew). Каталог — `~/.local/bin`, если он в PATH, иначе первый каталог PATH внутри домашнего, куда можно
писать; системные каталоги вне домашнего требуют root, а установка его не просит. Подходящего нет — команды нет, а
`check -g` называет строкой `!` готовую команду, которая добавит `~/.local/bin` в PATH профиля оболочки и повторит
установку. С `--link` команда — ссылка на `bin/elves.ts` клона: его шебанг через `sh` работает и по ссылке, правка
клона видна сразу. Без `--link` — шим `exec bunx --silent @miroshnik/elves@<версия>` на релиз машины: каталог bunx
временный, а команда совпадает с каноном на машине, `update -g` переписывает шим вместе с ним. Своим установка
считает только свою ссылку (на `bin/elves.ts` вне `node_modules`) и шим со своей строкой-меткой: чужой `elves` —
свой скрипт пользователя, глобальный пакет — остаётся, строка `!` в выводе `install -g` и `check -g`; `elves` раньше
по PATH, который терминал зовёт вместо команды машины, — тоже `!`. Отвергнуто (вопросы задачи): `~/.bun/bin` — часто
не в PATH; шим на последний релиз (`bunx @miroshnik/elves`) — команда разошлась бы с каноном машины; команда только
для `--link` — машина копией осталась бы без неё.

Клон Elves с `--link` даёт машине канон симлинком на себя — правка видна сразу. В самом клоне канон поэтому не должен
грузиться вторично: закоммиченного симлинка в `.claude/rules` у клона нет, а `.claude/CLAUDE.md` выключает чтение
корневого `AGENTS.md`, которое Claude Code делает сам, когда CLAUDE.md нет.

Вести ли задачу целиком без спроса — отвечать на её вопросы по рекомендации, коммитить, пушить, чинить CI и мержить
свой PR по зелёным чекам — решение проекта, а не флоу: `install` спрашивает об этом в терминале и хранит ответ в
`.agents/elves.json` (`auto`) — его видят другой чекаут и любой агент. По умолчанию «нет»: молчание не даёт
права на необратимое. В клон Elves флоу не ставится — канон в его корне; `install` пишет в нём только манифест: эту
настройку и язык, а поля, которые пишет сам проект, — `env` и `batch` — переносит тем же правилом, что в тонком
проекте (#672): с `"batch": true` Elves ведёт задачи пачками, и смена режима или языка в клоне молча выключала бы их.

Флоу написан по-английски — репозиторий публичный, — а агент работает с человеком на языке проекта: диалог, задачи,
промпты субагентам, документы, названия тестов спеки. Язык — тоже настройка проекта: `install` спрашивает его в
терминале или берёт из `--lang <код>` (BCP 47) и хранит в `.agents/elves.json` (`language`), `check` и хук
называют его в начале сессии. Новая установка без флага — `en`, язык флоу. У установки прошлой версии поля нет, а
флоу до него работал только по-русски — её язык `ru`, и `update` его записывает: обновление не меняет проекту язык.
Отвергнуто: копия канона на каждом языке — копии разошлись бы, а модель читает английские правила и работает на любом
языке; язык из локали машины — у агента без терминала она случайна.

Файлы флоу коммитятся, поэтому установка следит, чтобы git проекта их не игнорировал: без шима в коммите скрипт
`package.json` в CI и чужом чекауте падает на `. .agents/slot.sh`, без манифеста чужой чекаут не знает режима и языка
(#558, вопрос 4). Исключения пишутся блоком Elves в конце `.gitignore` — отрицание действует, только если идёт после
игнорирующего правила; каталог снимается цепочкой `!/.agents/`, `/.agents/*`, … ровно с файлов флоу, прочее в нём
игнорируется, как раньше. Каталог, исключённый личным правилом (core.excludesFile), — `❌` без исключения:
`/.agents/*` в проекте спрятал бы прочее в нём у всех. Шаблоны `CLAUDE.md`, `.claude/` и `vendor/` тонкому проекту
безразличны: его файлов там нет.

Облачные сессии флоу не поддерживает (#837, раздел `cloud-session`), и хук `SessionStart` облачной сессии, который
прошлая версия клала в `.claude/settings.json` проекта и клона Elves (#610), установка больше не ставит, а оставленный
прошлой версией убирает — `update` проекта (capability `elves#update`) и `install` клона; свои настройки и хуки проекта
она не трогает.

Проверки проекта — скрипты `package.json` `lint`, `typecheck`, `test` и `test:*` — установка оборачивает в
очередь машины `slot` (capability `slot`): их зовёт любой — агент, человек в терминале, `github pr premerge`, — и все
встают в одну очередь. Обёртка — `. .agents/slot.sh && <команда>`: шим зовёт `elves slot --for $$` пакета
проекта, в `if command -v elves`. Скрипт `package.json` видит `node_modules/.bin` проекта — очередь его версии;
без `elves` на PATH (CI до установки зависимостей, чекаут без пакета) команда идёт как есть, сбой `elves` роняет
скрипт его кодом — проверено в #552. Обёртку прошлой установки — команду строкой у `elves slot` — `update`
переписывает. `build` не оборачивается — его запускают хостинг и Docker, где шима или пакета может не быть; watch — долгий, занял бы слот
надолго. Обёртку, снятую руками, `check` называет несоответствием, `update` возвращает; `package.json` уходит в
коммит вместе с файлами флоу.

Обёрнутый скрипт, который зовёт turbo, теряет переменные очереди: turbo 2 в strict env mode пропускает задачам только
названные в `turbo.json`, и раннер без `ELVES_SLOT_CPUS` берёт машину целиком, а вложенный скрипт в `slot` без
`ELVES_SLOT` ждёт собственный слот. `install` и `check` предупреждают готовой строкой `globalPassThroughEnv` — она в
хэш кэша не входит, а `ELVES_SLOT` у каждого прогона свой. `turbo.json` не правят: его ведёт проект и в нём бывают
комментарии; в `check` это строка `!`, не отставание — `update` её не исправит.

Мерж без ревью человека приложение Claude Code отклоняет и при `auto`: его разрешает правило `Bash(gh pr merge *)`
в настройках разрешений машины, а оно действует на все её репозитории — шире проекта. Такое разрешение владелец
ставит своей рукой: `install` с auto правило называет, настройки машины не меняет — иначе о нём узнают из отказа в
конце первой задачи. Так же — TTL кэша подсказок Claude Code (#665, capability `elves#update`): час дороже записью, и это
цена владельца — `install -g` печатает ту же строку с его командой, что и `check -g`, `~/.claude/settings.json` не
трогает.

Агент ставит флоу на машину из своей песочницы, а она пускает не всюду: Seatbelt у Claude Code защищает
`.claude/skills`, и установка обрывается на симлинках, когда копии в `~/.agents/skills` уже легли. Порядок поэтому такой, чтобы
повтор довёл установку: выбывшие скиллы уходят, пока их ещё перечисляет старый манифест, а новый пишется до копий —
повтор признаёт их своими, а не чужими каталогами с именем скилла. Симлинк, который уже ведёт куда надо, не
пересоздаётся: иначе `update` в песочнице падал бы на каждом запуске, даже без нового скилла. Отказ в записи — код 2 и
строка с путём и той же командой для своего терминала, а не стек. Отвергнуто: признавать своими копии, совпадающие с
файлами релиза, — это помогло бы только повтору тем же релизом и не помогло бы при обрыве посреди копии.

Пакет называется `@miroshnik/elves` — так он публикуется в npm (#556; `elves` на npm занято), репозиторий — `elves`;
прежнее имя пакета — `elves`. Клон или ветка, ещё не получившие новое
имя, — тот же клон Elves: установщик узнаёт клон по обоим именам пакета, иначе `check` в такой ветке звал бы клон
отставшим, а `install` ставил бы в него флоу. Пакет под scope bun кладёт в `node_modules/@miroshnik/elves`, и SHA
установки по спецификатору установщик ищет под полным именем: иначе пакет релиза счёл бы себя пускателем из `main` и
перезапускался бы снова.

Пакет из npm (`npm i -g`, `bun add -g`, devDependencies проекта) — сам релиз: его версия `ГГГГ.ММДД.N` — тег
`vГГГГ.ММ.ДД.N`, а коммит `elves pack` пишет в `gitHead` его package.json. SHA в спецификаторе у него нет, и без этого
установщик счёл бы себя пускателем из `main` и перезапустился бы через `bunx github:` — по сети и из архива GitHub, а
не из npm. Поэтому `install` из пакета npm ставит релиз своей
версии без сети.

Команда флоу — этот пакет через bunx: `bunx @miroshnik/elves <команда>`. Так её называют канон и README, вывод
`check`, `update` и хука, подписи блока `AGENTS.md`, шима и блока `.gitignore` (#559, вопрос 1). Строку из вывода
агент запускает как есть, а пакет из npm — сам релиз, без перезапуска. Пускатель из `main`
(`bunx github:miroshnik/elves`) остаётся запасным путём README. Отвергнуто: npm только в текстах, а вывод установщика
— как был: канон и вывод разошлись бы.

Скилла `dashboard` во флоу нет (#834): его вкладку «Сессии» повторяют боковая панель и уведомления приложения, вкладку
«Оценка и факт» — `est period`; агенты звали его 126 раз в октябре и ни разу за 1–16 ноября. Машина прошлой версии
держит его каталог в `~/.agents/skills` и ссылку в `~/.claude/skills`: `install -g` и `update -g` убирают их, как любой
скилл из прежнего манифеста, которого в Elves больше нет, — `check -g` до обновления называет их отставанием, после —
молчит. С ним ушло то, что жило только ради него: API прокси `task-env` и экспорты `est` и `github`, которые никто
другой не импортировал.
