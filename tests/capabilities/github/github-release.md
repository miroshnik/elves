Выпуск пачки — та же модель, что у очереди диспетчера (#867), `skills/github/scripts/queue.ts`: состояния выпуска,
переходы между ними и шаг `batch release`. Команда собирает факты — PR выпуска, его проверки, PR, влитые в пачку, — а
что она делает в состоянии и какую строку `Next:` печатает, решает модель; действия (ребейз, PR, пересборка тела,
уборка worktree) и тексты шагов — в `github.ts`.

Зачем. #843 перевёл очередь на таблицу переходов, а `cmdBatchRelease` ветвился своими условиями: нет PR выпуска,
открыт, красный, влит — четыре ветки с `return` и своим `Next:` строкой внутри каждой, а выбор починки красного
выпуска (`fixSteps`) — ещё тремя условиями. По ответу 1 #843 выпуск — отдельной подзадачей: PR #843 вышел к ~1 500
строкам. Теперь правило выпуска — строка таблицы и тест на неё, справка «batch release» показывает те же таблицы, тест
держит её строки равными коду.

Состояния выпуска: нет, открыт, красный, влит. Состояние — чтение фактов: PR выпуска нет — «нет»; влит — «влит»;
открыт — по его проверкам (`checkStates` головы, как у `task show` и `ci-wait`) и по `pr premerge` на его голове:
упавшая или отменённая проверка или ❌ premerge — «красный», иначе «открыт», даже без проверок — голова сдвинулась, полный прогон пошёл заново. «Нет» без влитых в пачку PR задач —
отказ: выпускать нечего, PR выпуска не закрыл бы ни одной задачи. С PR выпуска отказа нет: влитое уже в нём.

Переходы — таблица `RELEASE_TRANSITIONS`. Свой переход `batch release` делает сам (`by` «batch release»: «нет» →
«открыт», PR открыт) и печатает шаг состояния, в котором оставил выпуск: шаг состояния — шаг его первого перехода с
шагом, как в очереди. Поэтому открытый только что и открытый давно печатают одни шаги — проверки, `pr premerge`, мерж;
красный — починку; влитый — шаги закрытия. «Влит» → «нет» — следующая пачка: очередь начинает её из влитого `main`
(#787 — только с готовой задачей), и пачка сессии — уже она, без выпуска.

Причины, которые не видны из таблицы:

- Открытый выпуск при каждом повторе пересобирает заголовок и тело по PR, влитым в пачку сейчас (#819): PR починки
  красного выпуска, влитый после открытия, нёс `Closes` второй задачи, тело собиралось один раз — и мерж выпуска её не
  закрыл. Красный — тоже: починка уже могла влиться.
- Красный выпуск чинится в пачке, а не откатывается (#650): полный набор впервые идёт на выпуске, PR остаётся открытым,
  остальные задачи ждут — новых исполнителей нет, их PR держит `pr premerge`. Починка влита — полный прогон заново на
  том же PR, второго PR нет.
- Починки нескольких виновных идут параллельно (#902, `fixGoesIn`): мерж первой сдвигает голову, прогон на ней идёт —
  выпуск «открыт», не «красный», — и `pr premerge` держал вторую до закрытия выпуска, который без неё не позеленеет.
  Поэтому PR задачи выпуска проходит, пока выпуск красный и пока его прогон идёт заново после влитой починки; первый
  прогон и зелёный выпуск его держат — выпуск проверен без него.
- Влитый выпуск убирает worktree и ветки исполнителей пачки (#698) по правилу очереди: диспетчер, который
  останавливается, очередь больше не зовёт, а worktree ждали бы её.
- Красный по `pr premerge` — тоже красный (#884, событие `premergeRed`): CI выпуска зелёный, а spec-red против main —
  ❌ у теста с пометкой «существующее поведение», верной против пачки, где поведение принесла задача пачки, и неверной
  против main. Выпуск, красный только по чекам, оставался открытым: `pr premerge` PR починки держал его до закрытия
  выпуска, а выпуск был красным именно из-за неё — круг; обход владельца — закрыть выпуск и выпустить заново. ❌
  `pr premerge` оставляет метку на голове выпуска с файлами своих строк — по ним виновная называется, как по логам
  упавших джобов; починка влита — голова сдвинулась, метка — прежней головы, тот же PR снова открыт.

Починку красного выпуска выбирает модель (`redFix`), первую, что выполнена: открыт PR починки задачи выпуска в пачку —
ждать ответа её исполнителя, виновную не искать и бисект не гонять; виновная названа (единственная задача выпуска, по
меткам решений упавших тестов — #650, #689 — или бисектом) — её починка; не названа очередью — её называет `batch
release`: бисект по границам задач идёт на машине минутами, очередь его не гоняет; не названа после бисекта — диспетчер
по логам упавших проверок или владелец. Красный только по `pr premerge` — без бисекта (`bisectable`): он воспроизводит
на машине упавшую проверку CI, а здесь все тесты зелёные — не назван по меткам, диспетчер читает строки ❌ `pr premerge`.
`fixSteps` только печатает выбранное — одним текстом для очереди и выпуска.

Отвергнуто для красного по `pr premerge` (#884): статус коммита на голове выпуска — запись в GitHub ради факта одной
машины, где диспетчер и исполнители делят каталог конфигурации, как метку пройденного premerge; spec-red заново в
очереди и `batch release` — минуты на каждый вызов, а вердикт на этой голове уже есть.

Отвергнуто: отдельный файл модели выпуска — у выпуска и очереди общие акторы и правило «шаг — первого перехода с
шагом», а очередь читает открытый и красный выпуск сама (её шаги `releaseSteps` и `fix`); состояние «закрыт» после
`task close` задач выпуска — `batch release` его не читает: после мержа он печатает шаги закрытия, пока PR выпуска
влит.
