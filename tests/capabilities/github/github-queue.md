Очередь диспетчера — модель в коде (#843), `skills/github/scripts/queue.ts`: состояния задачи в очереди и её
исполнителя, переходы между ними и шаг диспетчера. `task queue` собирает факты задачи — GitHub, git, выдачи сессии — и
печатает строки `+`, `=`, `○` и `Next:` из модели; сама модель ничего не читает, и каждое правило проверяется без сети
и git.

Зачем. За 1–16 ноября 89 % вызовов инструментов шли в субагентах диспетчера, на диспетчер и пачки — 15 % задач Эльфов и
3 из 7 последних починок. Протокол был прозой: «task queue» в справке — абзац на 114 строк с полутора десятками
ссылок на инциденты, «batch release» — ещё около 85, а состояния задачи и условия переходов — условиями внутри одной
функции `cmdTaskQueue`. Починка одного случая меняла соседний, и проверить, что задача не потерялась между `+`, `=` и
`○`, можно было только сценарием с поддельным GitHub. Теперь правило — строка таблицы и тест на неё; справка
показывает те же таблицы, а тест держит её строки равными таблицам кода.

Состояния задачи: не готова, готова, выдана, PR открыт, влита в пачку, выпуск открыт, выпуск красный, выпущена,
закрыта. Состояние — чтение фактов, а не запись: очередь ничего не хранит, кроме выдач и ветки пачки, и после
перезапуска приложения читает то же. Выпущена — в ветке по умолчанию, хвост (деплой, актуализация, `task close`) не
кончился: своим PR — хвост исполнителя, строка `=` держит его worktree и зависимые задачи (#769: «Closes #N» закрывает
issue при мерже, а исполнитель ещё ждёт деплой); выпуском пачки — хвост диспетчера, его печатает `batch release`, строки
в очереди нет. Роль задачи в работе для выпуска: живой исполнитель пачки держит выпуск, влитая в пачку — готова к нему,
задача мимо пачки (PR в main, «В работе» без выдачи, `--main`) выпуск не держит (#696).

Переходы — таблица `TRANSITIONS`: из состояния по событию в состояние, кто его делает и шаг диспетчера, пока задача
ждёт этого перехода. Шаг очереди (`Next:`) — первый в порядке `STEPS` из шагов её задач и открытого выпуска: починка
красного выпуска, шаги открытого выпуска, выдача готовых, ожидание исполнителей пачки, выпуск, ожидание задач мимо
пачки, «очередь пуста». Выпуск — пачки, а не задачи: группа `--tasks` без его задач видит его тоже. Тест на каждый
переход — факты до события читаются исходным состоянием, после — целевым, и таблица даёт то же; переход без случая в
тесте — красный тест. Ссылки на инциденты, из которых выросло правило, живут в названиях этих тестов и здесь, а не в
справке: справка говорит, что делать, история — тут.

Причины переходов, которые не видны из таблицы:

- Выдача — запись `--assignment` в `dispatchers/<id>.tasks`, а не «В работе» (#513): исполнитель ставит его после
  вопросов задачи, и до того очередь выдавала задачу второму. Выдача живёт всю сессию: ответ исполнителя не делает
  задачу готовой — «влито» закрывает её, вопрос ждёт владельца, «ждёт субагентов» ответит снова, «сломалось» не
  перезапускается.
- Открытый PR — строка `=` со ссылкой (#513): задача, чей исполнитель ждал CI, была `○` и выпала из обоих списков.
- Блокер, влитый в эту пачку, задачу той же пачки не держит: её исполнитель ведёт ветку от пачки (#648); влитый в другую
  пачку или не влитый — держит, как без пачек. Блокер, закрытый мержем, держит до своего `task close` (#769).
- Открытый выпуск придерживает готовые задачи (#649): влитое в пачку сейчас поменяло бы то, что проверил его CI.
  Красный выпуск чинится в пачке, а не откатывается (#650): виновную по меткам решений называет очередь, бисект —
  `batch release`; починка — PR виновной в пачку, затем полный прогон на том же PR выпуска.
- Новая ветка пачки — только с готовой задачей (#787): иначе на origin оставалась пустая ветка без выпуска.

Исполнитель: работает, ответил, ждёт субагентов, упал — по его ответам (`EXECUTOR_TRANSITIONS`). Скрипт видит только
worktree: блокировка живым процессом или HEAD, сдвинутый за 15 минут, — работает (Claude Code не блокирует снова
исполнителя, продолженного через SendMessage, #533, #565); субагент без своего worktree работает в его каталоге —
ждёт субагентов (#571: актуализация эпика шла в каталоге ответившего исполнителя, и очередь убрала его); иначе —
ответил: «упал» отличает только ответ, его получает диспетчер. Живой исполнитель — работает или ждёт субагентов:
перезапуск при нём отказывает (#565: исполнитель #545 ответил «сломалось», ответы его субагентов разбудили его, и он
влил задачу, пока рядом работал второй), его worktree очередь не убирает. Сдвинутый HEAD очередь для уборки не читает:
`task close` сам отцепляет worktree на `origin/<base>`, и HEAD ответившего исполнителя сдвигается последним.

Своя уборка worktree исполнителей нужна (проверено 2026-11-17 по документации Claude Code, «Worktrees» и «Claude
directory»). Worktree субагента Claude Code убирает сразу только без изменений; с коммитами — периодической чисткой,
когда он старше `cleanupPeriodDays`, и она оставляет worktree с незапушенными коммитами: коммиты субагента
исполнителя, перенесённые в ветку задачи, на его собственной ветке так и остаются незапушенными, а выпуск пачки
переписывает коммиты задачи (#816). Очередь убирает по фактам задачи — влита и закрыта, — а не по возрасту. Срок
`cleanupPeriodDays` та же чистка применяет к транскриптам: `est fact` читает транскрипты задачи до её `task close` —
дни и недели, `est period` сравнивает периоды до и после смены флоу — месяцы; поэтому на машине остаётся 365, хотя
оценок до работы больше нет.

Отвергнуто: Workflow Claude Code — сценарий не принимает ввод пользователя посреди запуска, а диспетчер передаёт
вопросы исполнителей и «да» на мерж; agent teams — экспериментальные. Диспетчер остаётся своим. Выпуск пачки на той же
модели — следующей подзадачей (ответ 1 задачи): этот PR — модель и очередь.
