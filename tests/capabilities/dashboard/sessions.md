При двух-трёх десятках параллельных сессий владелец спрашивает одно и то же: «не зависло ли?», «что с этой
сессией?», «что за задачи висят?» — и отвечает себе обходом сессий руками; вопросы к нему разбросаны по ним. Поэтому
страница открывается вкладкой «Сессии»: строка на задачу «В работе» — её сессия и чего та ждёт, сверху — «Ждут
владельца». График оценок — вторая вкладка: его смотрят после правки флоу, а сессии — каждый час.

Сессия задачи — по файлу закрепления `github task status` (`sessions/<id сессии>` каталога конфигурации), а не по
эвристике названия или ветки: закрепление пишется в момент взятия задачи и однозначно. Чего сессия ждёт — по её
транскрипту: фоновая задача без уведомления о завершении (её разбудит уведомление), последний ход — ответ без вызова
инструмента (ход за человеком), записей нет дольше 15 мин (тишина); что именно ждёт фоновая — CI или деплой, — видно по
PR задачи. Транскрипт — единственный источник, который пишет само приложение: статус, который ставила бы модель,
врал бы ровно тогда, когда сессия зависла.

GitHub для вкладки — запрос на репозиторий без блокировки сервера, задачи «В работе» — фильтром проекта на стороне
GitHub: строки проекта целиком, с комментариями, по всем репозиториям читаются десятки секунд, а вкладка обновляется
сама каждые 30 с. Устаревший кэш отдаётся сразу, свежий собирается в фоне. Обновление — подменой `<main>`, а не
перезагрузкой: перезагрузка сворачивала бы раскрытые вопросы каждые полминуты.

Вопросы сессии без задачи «В работе» — только явные (строки конца сессии или абзац на «?»), рутины по расписанию не в
счёт: на настоящих сессиях блок без этого тонул в ответах вроде «за час заявок не было». Задачи бэклога с меткой
«вопросы» свёрнуты группой — их десятки, и они ждут, пока задачу возьмут, а не сейчас.

Отвергнуто: облачные сессии — их транскрипт в облаке, а проекты GitHub им закрыты, задачу они не закрепляют; видно
только, что PR задачи сделан облаком. Статус «тишина» по одному времени без фоновых задач — фоновое ожидание CI
молчит по полчаса и было бы ложной тревогой.

## Блок «Decided auto» — решения сессий в режиме auto

В auto сессия отвечает на вопросы задачи сама — рекомендацией с пометкой «✅ авто» в разделе вопросов (канон, «What I
do without asking»): владелец до первой правки кода отвечает теперь в единицах сессий из сотни, а «Ждут владельца»
показывает только открытые вопросы — решённого агентом не видно. Решение владельца 2026-10-14: сводка решений авто за
сутки на вкладке «Сессии» — посмотреть после факта, не останавливая сессии (#448). Поэтому блок внизу, под таблицей
задач: срочное — наверху.

Окно — по правке описания задачи (`lastEditedAt`, без правок — `createdAt`), а не по `updatedAt`: ответ пишется правкой
описания, а комментарий или закрытие старой задачи поднимали бы её давние ответы. GitHub отбирает задачи фильтром
`since` — он по любому обновлению и шире окна; состояние любое, эпики тоже: решение бывает в задаче, закрытой сегодня.

Пометку скрипт ищет значениями `autoAnswer` всех языков словаря в любом месте пункта: `task answer --auto` (#434) ставит
её перед вопросом, руками — и после вопроса, и на строке продолжения, а в проекте на `ru` встречается «✅ auto». Ответ
владельца пометки не несёт и в блок не идёт. Пометка посреди текста сама разделяет вопрос и ответ: рекомендация до
неё остаётся при вопросе, а жирная метка внутри ответа его не режет — на ответах Elves за сутки разбор по метке
резал ответ пополам. Пометка в начале или в конце — делит текст: жирная метка (`**Ответ:**` — формат `task answer`),
иначе первый «?», иначе первая строка, а одна строка — до « — ». Это эвристика для ручных форм: неточный раздел виден
глазом, вопрос и ответ целиком — по ссылке на задачу.

## Адреса сервисов задачи

У задачи «В работе» свой стек Docker Compose и свои адреса `<сервис>.<N>.<проект>.localhost` (скилл `task-env`), но
их надо знать: владелец открывает приложение задачи с дашборда одним кликом, а не собирает адрес из номера и имени
репозитория. Источник — маршруты прокси из его API по loopback, а не сокет Docker: доступ к Docker — доступ ко всей
машине, а маршрутам нужен только loopback. Маршрут появляется со стартом контейнера и пропадает с его остановкой — поэтому маршруты
читаются при каждом открытии вкладки, как закрепления, а не раз в минуту, как GitHub. Схему адреса знает скрипт
`task-env` (`taskAddress`, `hostProject`, `addressUrl`), дашборд её не повторяет.

Адреса e2e на вкладку не идут: стек e2e пересоздаётся на каждый прогон, ссылка на него живёт минуты (#396, вопрос 4).
Прокси не запущен — ссылок нет и ошибки нет: без прокси нет и адресов, а строка в плашке у каждого, кто Docker не
ставил, была бы шумом; любой другой сбой — плашкой, как ошибка GitHub (вопрос 5).
