# spec

Скилл `spec`: спецификация из тестов — харнесс механических проверок, документация `docs/spec`, требования PR в
`spec-diff`, исключения, доказательство поломкой, заявленный код, публикация спеки, шарды CI и проверки перед коммитом.

## precommit

Скрипт `precommit` скилла `spec`: проверки перед коммитом — одним вызовом, со строкой на проверку и подробностями
только упавших.

Набор проверок перед коммитом — `lint`, `typecheck`, `test:spec` и затронутые правкой тесты (`docs/testing.md`, «Run
and result») — агент гонял отдельными вызовами, а на каждом круге исправлений — снова все. Длинный вывод раннера уходил
в контекст целиком: ≈ 15 ходов на задачу в пяти проектах (#671, эпик #663). Ход дорог не сам по себе, а тем, что каждый
перечитывает растущий контекст.

Решение:

- одна команда — `elves precommit` пакета (`bun --no-env-file node_modules/.bin/elves precommit`), в Elves —
  `bun run precommit`; скрипты проекта идут менеджером пакетов проекта (`projectCommands` скилла `github` — стандарт
  `package-manager`), от корня git;
- все проверки стартуют разом: каждый скрипт уже обёрнут в очередь машины (скилл `slot`), и сколько их идёт вместе,
  решает очередь, а не команда; своей очереди у команды нет — её слот держал бы вложенные скрипты мимо очереди;
- `test` получает `--changed=<base>`: база по умолчанию — `origin/main`, в пачке — `--base origin/<ветка пачки>`;
  у npm аргумент идёт после `--`, у остальных — как есть;
- скрипта нет в `package.json` — строка `○`, не провал: у проекта может не быть линтера;
- строка на проверку — по мере окончания: `✅`/`❌`, что решило, время; в конце — подробности только упавших: их вывод
  без строк прошедших тестов и эха команды менеджера, последние 80 строк, и файл со всем выводом;
- результат тестовой проверки — по сводке раннера (`bun test`, Vitest, Jest, Playwright), а не по коду выхода
  (`docs/testing.md`): нет сводки — прогон не дошёл до конца, каков бы ни был код; упавшие тесты при коде 0 — провал;
  зелёная сводка при коде не 0 — тоже провал: ошибка вне тестов; у `lint` и `typecheck` сводки нет — решает код;
- коды: 0 — всё зелёное, 1 — проверка упала, 2 — ошибка вызова (аргументы, нет `package.json`).

Отвергнуто: скрипт `precommit` в `package.json` проекта, который ставит установка, — ещё одна строка, которую `check`
сверял бы с релизом, а команда пакета уже идёт версией проекта. Место — скилл `spec`: проверки перед коммитом — ворота
спеки (`checks.md`), а `slot` других скиллов не импортирует (стандарт `scripts#skill-imports`), менеджер пакетов же отвечает
только `github`.

## spec-break

Проверка решения обязана уметь упасть: `spec-break` доказывает это поломкой — правкой кода, от которой проверка
должна покраснеть. Агент выбирает поломку под одну проверку, скрипт применяет её, прогоняет тест и всегда
откатывает; ✅ «упал» — проверка ловит эту поломку, ❌ «не упал» — «покрыто» только на словах.

Нужен при переносе старой спеки и после ревью унаследованных тестов: руками поломку забывали вернуть при обрыве
сессии, а первый красный тест в serial-группе прятал остальные — поломки гоняли пачками в отдельных сборках.

Это не мутационное тестирование (отвергнуто в каноне: шум эквивалентных мутантов и давление к тестам на мелочи):
поломок столько, сколько проверок надо доказать, а результат — доказательство, а не метрика.

### Поломка всегда откатывается: файл возвращается в исходный вид, что бы ни случилось с прогоном

Поломку применяют к исходнику проекта: оставленная, она уйдёт в коммит. Откат — всегда: после прогона, по сигналу
и после обрыва без шанса на откат (kill -9, закрытая сессия) — тогда файл возвращает следующий запуск по журналу в
`.git`.

- ✅ откатывается, даже если прогон прерван
- ✅ обрыв без отката — следующий запуск возвращает файл по журналу
- ✅ файл правили после обрыва — журнал правку не затирает и говорит об этом

</details>

## spec-claims

Нет решения — нет кода: каждая точка входа системы (маршрут, страница, job, команда) вызывается хотя бы одним
тестом capability. Код, до которого не доходит ни одно заявленное поведение, — кандидат на удаление или
незаписанное требование.

Тестовое окружение пишет в журнал, какую точку входа и из какого теста вызвали (`journal` харнесса), а после
прогона всех тестов и шардов `spec-claims` сверяет реестр точек входа из кода с журналом. Результат — отчёт JUnit:
`spec-doc` кладёт его в спеку как обычный стандарт.

Сверка честна, пока id одни и те же: повтор id в реестре спрятал бы непокрытую точку за покрытой, а id журнала, которого
нет в реестре, значит, что формат разошёлся или реестр неполон, — оба случая красные. Журнал — только текущего прогона:
раннер пишет в свой каталог и стирает его в начале (`resetJournal`), иначе удалённый тест продолжает «вызывать» точку.

## spec-diff

Скрипт `spec-diff` скилла `spec`: ревьюер PR видит, какие требования PR снимает, меняет и добавляет, —
раздел «Спека (тесты)» для тела PR с названиями тестов.

Дифф тестов — дифф требований: удалённый тест — снятое требование, и оно не должно пройти незамеченным среди
сотен строк кода. Названия берутся разбором исходников на двух ревизиях парсером TypeScript, который лежит в скилле файлом, — без
прогона тестов, за секунды и в CI без установки зависимостей.

- ✅ без изменений — «Тесты не менялись»
- ✅ `<` в названиях вне code span экранируется — GitHub не съест `<type>` в теле PR

### Изменён — только очевидное переименование, иначе удалён и добавлен

Переименованный тест ищется только в том же файле и том же describe (похожесть имени ≥ 0,6); тест с тем же
именем под другим describe — в любом файле папки; тест с тем же телом — в том же файле, даже если сменились и
describe, и имя. Тело сравнивается без пробелов и завершающих запятых: перенос вызова prettier, когда название
стало длиннее строки, проверку не меняет. Порог высокий: спрятать снятое требование под видом переименования хуже, чем показать
переименование как удаление и добавление.

<details><summary>✅ 8 тестов</summary>

- ✅ непохожее имя в том же describe — удалён и добавлен, не переименование
- ✅ переименован describe — изменён, старый describe зачёркнут
- ✅ тот же тест под другим describe в другом файле папки — изменён: переехал в другой раздел
- ✅ тест с новыми describe и it и тем же телом — переименование

## spec-doc

Скрипт `spec-doc` скилла `spec`: документация `docs/spec` из тестов — страница на capability, правило
архитектуры и стандарт, которая читается рассказом: зачем, что умеет, чем проверено.

Требование существует, пока есть проверяющий его тест, поэтому документацию о поведении не пишут руками: её
собирают из отчётов раннеров и JSDoc тестов, и с тестами она не расходится. В `main` её нет: после мержа CI
собирает `docs/spec` и публикует в ветку `spec` (`spec-publish`).

## spec-exceptions

Исключения решения живут файлом на элемент — `exceptions/<элемент>.json` в папке решения, а не массивом в
`exceptions.ts`: подзадачи разбора долга параллельно убирают каждая своё исключение, и в общем массиве каждая
следующая получала конфликт соседних строк и повторный прогон CI. Удаление своего файла ни с чем не пересекается.

Проекту, где исключения ещё в `exceptions.ts`, переезд — одной командой: `spec-exceptions` раскладывает каждый файл
по каталогу, удаляет старый и меняет импорт в тестах папки на `exceptionsIn()` харнесса; что переписать не смогла —
называет. Харнесс на `exceptions.ts` в папке решения падает тестом с подсказкой этой команды.

Отвергнуто: сортировка массива — соседние удаления всё равно конфликтуют; `merge=union` в `.gitattributes` — при
удалении соседних строк возвращает обе, и снятое исключение молча оживает.

## spec-harness

Харнесс проверок скилла `spec`: соглашение о коде или поведении проекта проверяется механически, а тесты
проверки попадают в отчёт раннера и в спеку так же, как обычные.

Соглашение о поведении («каждая мутация пишет аудит») проверяется не на одном примере, а на каждом элементе
реестра, который берётся из кода: новый элемент не проскочит мимо. Пустой реестр и проверка, прошедшая на
заведомом нарушителе, — упавшие тесты: такая проверка ничего не проверяет.

Тонкий проект берёт харнесс и spec-скрипты из пакета `@miroshnik/elves` в devDependencies, без копии флоу (#556):
тесты импортируют `@miroshnik/elves/spec/harness` (и модель архитектуры, фрагмент ESLint, `github`, репортёр knip
`spec/knip-hints` — CommonJS без сборки, его `file` — путь для `knip --reporter`, #620), скрипты
`package.json` и CI зовут `spec-doc`, `spec-diff` и остальные `spec-*` бином пакета —
`bun --no-env-file node_modules/.bin/elves <скрипт>`, без env-файлов проекта (#596). Версия у
агента и у CI одна — версия пакета в lockfile проекта; пути — от каталога проекта, как у скрипта копии. Тест проекта
идёт под bun test: Bun берёт исходник TypeScript, раннер под Node — сборку для Node (стандарт `exports#harness-load`).

## spec-publish

Скрипт `spec-publish` скилла `spec`: после мержа в `main` CI публикует сгенерированную документацию `docs/spec` в
отдельную ветку `spec`, а не коммитит её в `main`.

`docs/spec` — производная копия тестов: в `main` параллельные PR конфликтовали бы в сгенерированных страницах и
оглавлении. Ветка `spec` читается в GitHub и агентом (`git show origin/spec:README.md`), каждая публикация помнит
SHA `main`, из которого собрана, и CI проверяет, что опубликовано ровно то, что собрано. Мерж, не менявший
документацию, — коммит с тем же деревом и новым SHA: ветка называет последний проверенный `main`, и `spec-diff`
отличает пропущенную публикацию от «без изменений».

Без CI на `main` публикуется `docs/spec` из прогона PR, и только когда этот прогон проверил `main` целиком: артефакт
назван по дереву merge-ref, а скрипт `spec-run` ищет его по дереву коммита мержа. Деревья равны, когда между стартом
прогона и мержем в `main` ничего не влили. Влит отставший PR — публикация пропускается: из его прогона она откатила
бы ветку `spec` (в ней не стало бы страниц PR, влитого раньше). Публикации приходят не по порядку мержей, поэтому
поверх более новой старая не публикуется.

Отклонённый пуш — не падение: ветку между чтением и пушем могла сдвинуть другая публикация или подвёл хостинг, и
красный job публикации на `main` мешал бы ожиданию деплоя. Скрипт пишет в лог причину из stderr `git push`, после
паузы перечитывает ветку и решает заново: собранная из потомка — пропуск, иначе коммит поверх новой головы; попытки
ограничены, исчерпаны — код 1 с причиной.

Следующая публикация поверх нашей — не расхождение (#443): сверка после пуша читает ветку с удалённого, и между пушем
и чтением поверх могла лечь следующая публикация — дерево ветки уже не наше, сверка давала код 1 при удавшемся пуше.

newer»); в лог — строка, чем ветка ушла дальше. Нашего коммита в ветке нет (её перезаписали) — код 1, как раньше.

Флаг раннера `--shard` на время не смотрит. Playwright делит сьют подряд по числу тестов в порядке путей, Vitest —
файлы по хешу пути. Тяжёлые тесты одной папки достаются одному шарду: PR ждёт его, остальные простаивают. В проекте на
флоу шарды Playwright с равным числом тестов расходились по времени больше чем вдвое.

Раскладка жадная: файлы от самого долгого — в самый лёгкий шард. Длительности — из тех же отчётов, что читает
`spec-doc` (JSON Vitest, JSON Playwright, JUnit `bun test`): шаблон CI уже собирает их артефактом `spec-reports` джоба
`spec`, а `spec-run --artifact` находит последний зелёный прогон с ним. Файл длительностей в репозитории отвергнут:
он устаревает и требует коммитов. Нет отчёта — первый прогон, артефакт истёк — файлы делятся поровну по числу; новый
файл без замера получает среднюю длительность.

Источник длительностей один на все шарды прогона. «Последний зелёный прогон» меняется, пока шарды доходят до шага:
прогон другого PR, завершившийся между их запросами, давал шардам разные раскладки — в проекте с тремя шардами e2e 22
файла из 101 не прошли нигде, и CI остался зелёным. Поэтому в Actions `spec-run` берёт прогон, зелёный к началу первой
попытки текущего, — тот же ответ получает и повтор упавших шардов. Отдельный джоб, который выбирает прогон один раз и
отдаёт его шардам, отвергнут: каждый шард стартовал бы позже на время этого джоба. Сбой запроса — красный шард, а не
раскладка по числу рядом с раскладками по длительностям.

Файлы шарда уходят раннеру позиционными аргументами вместо `--shard`, а это фильтры: у Playwright — регулярные
выражения по абсолютному пути, у Vitest — подстроки пути. Путь, который входит в другой путь (`tests/a.test.ts` в
`packages/web/tests/a.test.ts`), взял бы чужой файл: тот прошёл бы в двух шардах или ни в одном. Поэтому фильтр
Playwright экранирован и привязан к концу пути, а файлы, чей фильтр всё же берёт другой файл, идут в один шард. У bun
test путь без `./` — тоже подстрока, а с `./` — путь файла: фильтр `--runner bun` — `./<путь>`, он берёт ровно свой
файл. `--runner vitest` у проекта на bun test тоже работал — подстрока пути, — но склеивал в один шард файлы с общим
путём, а имя раннера в CI и в проверке раскладки отсылало к Vitest, которого в проекте нет.
Проект-зависимость Playwright (вход перед тестами) фильтры не режут: раннер добавляет его в каждый шард сам.

Единица раскладки — файл: файл дольше доли шарда остаётся пределом, его делят на файлы.

### Шарды одного прогона берут длительности из одного прогона

«Новейший зелёный прогон» — не постоянная: между запросами шардов одного прогона может завершиться зелёным прогон
другого PR. Шарды тогда раскладывают файлы по разным отчётам, раскладки расходятся: одни файлы идут в двух шардах,
другие — ни в одном, и CI зелёный без них — в проекте с тремя шардами e2e так пропало 22 файла из 101. Поэтому в
Actions источник — новейший прогон, зелёный к началу первой попытки текущего (`GITHUB_RUN_ID`): ответ один, когда бы
шард ни дошёл до шага. Сбой запроса — красный шаг: шард, разложенный по числу рядом с шардами по длительностям,
терял бы файлы так же.
