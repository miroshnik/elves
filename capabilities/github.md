# github

Скилл `github`: проект GitHub и задачи репозитория по канону `AGENTS.md` — команды `project …`, `task …` и `pr …`.

## github-premerge

Скилл `github`, `pr premerge`: перед мержем зелёного PR агент проверяет, что он совместим с `main`, который ушёл
вперёд после его CI, — и не вливает PR, который сломает `main`.

Без очереди мержа (эпик #206) PR вливается по своему зелёному CI, а CI проверил слияние с тем `main`, что был на
момент прогона. Замер #211 (CI 11 минут, 88 влитых PR за сутки, 20–30 параллельных сессий): 5 поломок `main` от двух
зелёных PR, одна покрасила 6 чужих PR. Все пять — проверки над всем кодом («реестр + инвариант», стандарты): один PR
убрал элемент, другой, зелёный против старого `main`, на него ссылается; первый был в `main` за 1–23 минуты до мержа
второго. CI на push в `main` там нет — красный `main` видят только следующие PR.

Поэтому `pr premerge` после PASS `ci-wait` и до `gh pr merge`: `main` не двигался после CI — CI проверил ровно это
слияние, вливать; ушёл — слияние головы PR со свежим `main` во временном worktree и быстрые проверки проекта (скрипт
`test:spec`: стандарты и архитектура — там все пять поломок, минуты, а не весь `test`). Красное или конфликт — код 1,
не вливать: чинить корень в PR. Окно остаётся: PR, влитый за время самой проверки, поймает CI следующего.

Typecheck на слиянии (#292). Семантический конфликт двух PR, влитых почти одновременно, — один убрал функцию, другой,
влитый в `main` после CI первого, её зовёт — стандарты не видят, а typecheck ловит за секунды: `premerge` проверил
слияние одним `test:spec`, и `main` упал на typecheck. Поэтому быстрые проверки — скрипты `package.json` по порядку
CI, какие есть: `typecheck`, затем `test:spec`, до первой красной; вывод называет ошибки компилятора. Ошибки на
слиянии и на голом `main` сверяются без позиции в файле: правка PR выше по файлу её сдвигает, а ошибка та же.
Тайпчек на `bun check` (Bun 1.4.3, #376) под агентом (`CLAUDECODE=1`) печатает ошибку XML-блоком с текстом на
следующей строке, а не строкой tsc — `premerge` приводит блок к строке tsc и называет её так же.

Что проверил CI, GitHub не хранит: merge-ref пересобирается, `pull_requests` прогона после мержа пуст. Поэтому по
времени: момент CI — самый ранний check suite головы PR, движение `main` — последнее событие ветки (Activity API,
REST: квота GraphQL общая на все сессии). Merge-ref строится до check suite — событие в минуту до него считается
уходом; чеков нет или событие не прочитано — тоже: неизвестное проверяется, лишняя проверка стоит минут, пропущенная
— красного `main`.

Красный `main` — не этот PR (#282). Без CI на push в `main` его видели только следующие PR: каждая сессия чинила его
в своём PR или ждала вслепую, а владелец рассылал «не пушить». Поэтому слияние красное — упавшая проверка ещё и на
голом `main`: красная тем же — код 3 «`main` красный», не вливать и в своём PR не чинить; PR ломает сверх красного
`main` — код 1 с его тестами и ошибками компилятора. Красный чек последнего коммита `main` (деплой, смоук; последний
прогон каждого имени, отменённый — не красный) — тот же код 3 до проверки слияния. Чинит один баг «`main` красный…»
на всех: `premerge` находит открытый поиском или печатает команду завести, остальные ждут его закрытия фоновой
командой `wait-ci.sh issue <N>`. PR, который этот баг закрывает (`Closes`), — починка: красный `main` его не
останавливает, иначе починку не влить.

Публикация спеки — не красный `main` (#443): упавший job `spec-publish` на последнем коммите (гонка пуша в ветку
`spec`) давал код 3, блокировал PR и заводил ложный баг «`main` красный», хотя код `main` был зелёным. Публикация
выкладывает документацию и ничего не проверяет, поэтому её check-run (`spec-publish` и `<job> / spec-publish` из
реюзабельного workflow) в красные чеки `main` не входит — строка `○` называет его, рядом с настоящим красным чеком он
не попадает ни в причину, ни в заголовок бага. Имена — те же, что у `wait-ci.sh`: обе копии правила держит одна
таблица (стандарт `scripts#spec-publish-job`).

Ждать — бага, чей заголовок называет упавший чек (#338). Открытый «`main` красный…» бывает от другой поломки — старый
баг на чек, который уже зелёный: сессия ждала его закрытия, а `main` он зелёным не делал, бага на настоящую причину
никто не заводил. Имя чека — целиком: `test` не в «test:spec». Починку так не сверяем: одна поломка названа то скриптом
(слияние красное на голом `main`), то чеком CI коммита `main` — строгая сверка не дала бы её влить.

Регрессия задачи — не баг «`main` красный…» (#699, эпик #645). После выпуска пачки `main` покраснел на шаге
установки из задачи пачки; задачу переоткрыли, её починку (`Closes` этой задачи) `premerge` остановил кодом 3 «жди
баг»: бага «`main` красный…» не было — баг здесь сама переоткрытая задача, и PR влили вопреки коду. Поэтому починка —
и PR, чей `Closes #N` называет задачу красного пуша: `Refs #N` или `Closes #N` коммитов check suite красного коммита
(от его `before`, без него — сам коммит) или `Closes #N` влитого ими PR выпуска. PR другой задачи ждёт, как прежде:
правило «не чинить в своём PR» — про чужие PR. Упавший шаг без теста (установка, сеть) метки решения не имеет —
заголовок бага называет чек и его упавший шаг из job'а GitHub Actions: «`main` красный: чек CI (шаг Install zsh)».

Стандарты без `test:spec` (#442). Проект со стандартами или архитектурой, но без скрипта `test:spec` проверялся на
слиянии одним typecheck или ничем, и строка «нет быстрых проверок» не говорила, что пропущено: в одном проекте 89
запусков premerge ничего не проверили, в другом стандарт покраснел на `main` сразу после мержа. Теперь `premerge`
называет строкой `○`, какие корни спеки на слиянии не проверены, и отсылает к `check` проекта — тот требует скрипт и
печатает его строку. Мерж это не останавливает: скрипт — настройка проекта, а не поломка этого PR.

Голова PR — по SHA (#505). GitHub создаёт `refs/pull/<N>/head` с задержкой: на одном PR ссылка появилась через 15
минут после создания, когда CI уже прошёл и `main` ушёл, — `premerge` дважды вышел с кодом 2, слияние проверяли
руками. Поэтому голову `premerge` берёт с origin по SHA из API: достижимый коммит (от ветки головы,
`refs/pull/<N>/merge`) GitHub отдаёт и до появления ссылки. Код 2 — когда голову не получить и по SHA: на origin её
нет.

Отвергнуто: проверять всегда — при 20–30 сессиях почти каждая ветка отстаёт, и проверка шла бы на каждый мерж, хотя
CI на merge-ref уже проверил это слияние; сравнение с merge-base ветки — то же «всегда»; CI на push в `main` — видит
поломку уже после мержа.

PR в ветку пачки (#649, эпик #645). Выпуск пачки живых исполнителей не останавливает (вопрос 2 эпика), а `premerge`
— шаг, который исполнитель делает перед каждым мержем, поэтому здесь его и ведут: PR выпуска пачки открыт — код 1 и
ожидание его закрытия (`wait-ci.sh issue <PR выпуска>`), влитое сейчас изменило бы выпуск, проверенный CI; выпуск
влит — код 1 и переход: в следующую пачку диспетчера (из маркера его сессии — у субагента тот же id), без неё — в
`main` с полным CI, тогда задача выходит из пачки и идёт обычным путём, с деплоем и `task close`; затем ребейз на новую
базу — коммиты пачки уже там, с другими SHA, и rebase-мерж GitHub повторил бы их. Выпуск закрыт без мержа или его нет
— проверка как обычно. Ту же причину ловит и проверка слияния у любого PR: коммиты головы, чьи изменения в базе уже
есть (`git cherry`), — код 1 и ребейз; PR из выпущенной пачки в `main` переводит и сам GitHub, удаляя голову влитого
выпуска в репозитории, что удаляет головы при мерже, — тогда исполнитель о переходе узнаёт только так.

PR в ветку пачки CI не запускает (#676), ветка пачки — тоже: ворота такого PR — проверки перед коммитом исполнителя, и
проверено ими само дерево головы, а не слияние, которое собрал бы CI. Поэтому `premerge` решает не по времени CI, а по
git: голова на свежей ветке пачки — вливать, ничего не прогоняя; пачка ушла вперёд после ветки PR — быстрые проверки на
слиянии с ней, как при ушедшем `main`; красное — правка и снова `premerge`, без `ci-wait`. Красные чеки последнего
коммита ветки пачки не читаются — их там нет. Переход в следующую пачку после выпуска — тоже без `ci-wait`, в `main` — с
ним.

### PR в ветку пачки CI не запускает — что проверено, premerge решает по git

PR задачи в ветку пачки CI не запускает (#676): проверки перед коммитом исполнитель прогнал сам, второй прогон того же
набора в CI держал его слот ожиданием. Что проверено — сама голова PR, а не слияние, которое собрал CI: premerge
решает по git — голова на свежей ветке пачки — вливать без проверок; пачка ушла вперёд — быстрые проверки на слиянии

## github-project

Скилл `github`, `project check` и `project fix`: проект GitHub любого репозитория устроен одинаково — по канону
`AGENTS.md`, и агент приводит его к канону одной командой.

Руками проекты расходятся: где-то выключен «Item closed», где-то фильтр прячет задачи с доски, и задачи ведутся
мимо канона. `check` показывает каждое расхождение пунктом ✅/❌, `fix` исправляет то, что умеет API, чего в API
нет — оставляет шагом UI со ссылкой, а удаление и настройки организации делает только после подтверждения.
Сверка и исправление — одна функция, поэтому `check` и `fix` не расходятся.

Вид проекта — как у эталона (#634): колонки «Доски» и «Таблицы» с прогрессом подзадач, «Таблица» сгруппирована по
Status, цвета вариантов Status и семь workflow эталона, с автоархивом закрытых задач. Проекты, заведённые до копии
эталона или правленные руками, проходили check, а выглядели по-разному: в «Таблице» стояли колонки «Роадмэпа», закрытые
задачи копились на доске. Колонки и цвета `fix` ставит через API, группировку и workflow — шагами UI. Сверяется только
то, что читает публичный API: срез, иерархия подзадач, ширина колонок, описание и README проекта в канон не входят;
описания вариантов Status — содержимое проекта, их `fix` не трогает.

Туда же — правило основной ветки: ветку с красным обязательным чеком GitHub не вливает сам. Правило канона «мерж
только при зелёных чеках» держит настройка, а не память агента. Обязательны чеки, зелёные на каждом из последних
влитых PR, а чек, переставший приходить, из списка уходит — PR не ждут его вечно. Актуальной ветки правило не
требует: несовместимость двух зелёных PR покажет CI следующего PR. Отвергнуто: strict и очередь мержа (#138, #149) —
за три недели не поймали ни одной поломки, а каждый чужой мерж стоил ребейза и повторного прогона CI; один
обязательный чек — «зелёные чеки» остались бы дисциплиной; ruleset без обхода admin — не прошёл бы прямой push
владельца (Elves так правит правила).

Свой ruleset называется `elves`.

Способ мержа — только rebase, и это тоже держит настройка: merge commit и squash выключены, rebase включён. Правило
мержа одно для всех репозиториев (`gh pr merge <N> --rebase`), агент не выясняет способ на каждом мерже, а в основную
ветку уходят сами коммиты ветки — история линейная. Отвергнуто (#254): способ по настройке каждого репозитория —
лишний ход на каждом мерже и отказ GitHub, когда правило называло выключенный способ. GraphQL настроек мержа не
меняет, поэтому `fix` здесь шлёт запрос REST.

Канон сверяется на языке проекта — `language` манифеста `.agents/elves.json` в корне чекаута. Без манифеста язык
неизвестен, и `check` с `fix` отказывают кодом 2 до первого запроса — с причиной и выходом: скопировать манифест из
основного чекаута или закоммитить его там (#681). Прежде язык без манифеста молча был `en`: в проекте на `ru`, где
`.agents/` не в git, свежий worktree остался без манифеста, `check` выдал шесть ❌ на настроенный проект, а `fix` по
ним переписал бы поля, представления и варианты `Status` под английские имена. Так же отказывают команды задач, что
пишут имена, `pr labels` и `batch release`; чтение разбирает имена любого языка словаря и идёт. Репозиторий совсем без
Elves отказывает так же (вопрос 2): одно правило без догадок по `package.json`, а молчаливый `en` и был поломкой.
Отвергнуто (вопрос 1): отказ только у `check` и `fix` — английские имена в проект на `ru` молча пишут и команды задач;
отказ и у чтения — без манифеста оно не ошибается.

## github-task

Скилл `github`, `task new`, `task show`, `task answer`, `task edit`, `task start`, `task status`, `task actualize`, `task close`, `task finish`, `task resume`,
`task queue` и `task drop`: задачу заводят, читают, отвечают на её вопросы, двигают по доске, закрывают после мержа и
снимают одной командой, и она всё время по канону `AGENTS.md`.

Заведённая руками задача остаётся без статуса, приоритета или связи с эпиком — и выпадает с доски и из оценки
эпика. Команда ставит всё сразу: тип или метку, проект и `Бэклог`, `Priority`, эпик, blocked by, milestone, а
проверяет всё до создания — задача не появляется наполовину. Оценку `task new` ставит сам, как `task close` — факт:
`est estimate` по типу ветки (`--branch-type`), аналоги подбирает скрипт. Отдельным шагом агент открывал скилл `est`,
гонял историю всех репозиториев и подбирал аналоги руками — до 10 минут на задачу (#381), а точнее механики это не было. Статус подзадачи тянет за собой эпик, закрытая без
выполнения уходит из проекта.

Задачу читали и правили руками: ручных `gh` в сессиях больше, чем вызовов скриптов (3 664 против 1 621 в одном
проекте), `gh issue view` — ~1,1–1,2 тыс. на проект, медиана 4 на сессию: описание, эпик, его подзадачи, PR и его чеки
— по отдельности. `task show` печатает их одним выводом, вместе с открытыми вопросами задачи и эпика — их канон велит
прочитать первыми; PR, который GitHub ещё не связал с задачей, находится по ветке, как в `task close`. Комментарии
задачи и эпика — тоже (#651): канон велит сверить вопросы с тем, что уже ответено, «комментарии, код», а без них ответ
человека комментарием исполнитель не видел и спрашивал заново или отвечал «✅ авто» поверх него. Свои комментарии флоу
(оценка и факт `est`, отчёт актуализации, «закрыта по PR») — строкой без текста: их читают скрипты, а не агент;
«Состояние» — целиком: это передача работы. Комментарий с пунктом `k.` к открытому вопросу k — или свободным текстом, к
каждому открытому — строка `?` у вопроса: ответ ли это и на какой вопрос, решает агент, а `task answer` переносит его в
описание. `gh issue edit
--body-file` — 280 раз, чаще всего ради ✅ у вопроса: агент переписывал описание целиком ради одной строки. `task answer`
ставит ✅ и «**Ответ:** …» у вопроса k — тем словом, которое `est` вычитает из размера описания, — нумерация и остальное
описание не меняются, а последний ответ снимает метку вопросов. Отвеченный вопрос команда не трогает: смена ответа —
решение, а не пометка. Ставит метку `task new` — когда в описании есть вопрос без ✅, а метки в репозитории нет — создаёт
её (#536): по ней задачу с открытыми вопросами видят дашборд («Ждут владельца») и очередь. Руками в пилоте #471
диспетчер ставил её шести задачам и раз промахнулся — поставил на PR вместо задачи, угадывая номер.

Остальная правка описания — тоже три хода: `gh issue view --json body`, правка в файле, `gh issue edit --body-file`; за
две недели в пяти проектах ≈ 2200 чтений описания и ≈ 480 перезаписей (#670). `task edit` правит описание одним вызовом:
замена текста (`--replace`), пункт в раздел (`--add`, вид пункта — по последнему пункту раздела), отметка пункта
(`--check`), несколько правок по порядку и одной записью. Замена текста, который встречается дважды, или отметка, которой
подходят два пункта, — отказ без изменений, а не первое совпадение: правка не того места незаметна, а длиннее текст —
один повтор вызова. Отвергнуто: отдавать описание файлом и принимать его обратно — тот же круг из трёх ходов.

Сессия ведёт одну задачу: `task status "В работе"` закрепляет первую за сессией и отказывает другой. Правило «Сессия =
задача» прозой не держалось: за три недели 41 из 94 сессий с работой вели больше одной задачи (в 31 вторую назвал сам
пользователь), и в 19 из 36 многозадачных привязка факта `est` по названию сессии ломалась. «В работе» зовёт каждая
сессия — это точка для механизма: на той же истории отказ второй задаче останавливает 20 из 20 многозадачных сессий и
не даёт ложных отказов в 83 остальных. Ключ закрепления — id сессии (`CLAUDE_CODE_SESSION_ID`), а не чекаут: worktree сессии
переиспользуют, ключ «чекаут» дал бы 42 ложных отказа. Задача, заведённая в сессии с закреплённой, остаётся в «Бэклог»:
`task new` велит спросить владельца, ставить ли её в очередь, и печатает промпт её исполнителя (ниже, #546).

Другую задачу сессия отдавала карточкой новой сессии (`spawn_task`): её запускал владелец кликом, а сессия о ней больше
не знала (#546). Теперь вместо карточки — вопрос владельцу «ставить #M в очередь?», а на новый эпик — «запускать
диспетчера на задачи эпика #M?»: `task new` в сессии с закреплённой задачей и отказ `task status` печатают вопрос и
промпт исполнителя, `task new` эпика — команду его очереди. На «да» текущая сессия сразу запускает исполнителя фоновым
субагентом — и сессия со своей задачей: запрет очереди в ней снят, её закрепление остаётся. Исполнитель делит id
сессии, поэтому `--assignment` пишет выдачу в любой сессии, кроме закреплённой за этой же задачей: иначе его «В
работе» отказало бы закрепление сессии, а в сессии ещё без задачи — закрепило бы её за задачей исполнителя.
Выданную задачу `task status` не закрепляет, а `est` отдаёт записи субагента с «Задача #N» в задании задаче N, а не
закреплению сессии. Отвергнуто: задача ждёт в «Бэклоге» с меткой очереди отдельную сессию-диспетчер владельца — «да»
не становится работой без ещё одного запуска; сессия становится диспетчером, только если у неё нет своей задачи, —
тот же ручной запуск для самого частого случая, находки по ходу задачи.

Фоновое ожидание `ci-wait` умирает с процессом приложения: при перезапуске четыре сессии потеряли ожидания в одну
минуту, и владелец 17 раз писал «продолжай» (#433). `task resume` называет возобновлённой сессии, что перезапустить, по
её закреплённой задаче: открытый PR — ожидание его чеков, влитый при открытой задаче — деплой и `task close`; готовой
командой, а не прозой «проверь, чего ты ждал». Репозиторий — из закрепления, а не из чекаута: хук зовёт команду из
каталога сессии, а он бывает чужим. Без закрепления — ни строки и ни запроса в GitHub: у сессии нет задачи.

Закрытие после мержа шло фазами друг за другом — деплой, `task close`, актуализация блока субагентом: по 200 закрытиям
медиана от мержа до конца сессии 8,5 мин, 12 ходов на пиковом контексте, больше половины времени — ходы модели
(прочитать справочник, собрать задание субагенту, сверить его ответ). Актуализация от деплоя не зависит — идёт
параллельно с ним, до `task close`; задание субагенту печатает `task actualize`, и где актуализировать нечего (нет
эпика, нет открытых задач в нём), говорит это строкой. Задачи эпика в задании — его подзадачи (sub-issues) из GitHub:
описание эпика списка задач и их связей не держит (#426) — копия устаревает с первой правкой связи, а субагент,
сверявший пометки в тексте со связями, правил её вместо того, чтобы убрать.

Ветку worktree (`claude/<слаг>-<хеш>`) в ветку задачи переименовывает `task status N "В работе" --branch
<type>/<N>-<slug>` — тем же вызовом, что берёт задачу. Руками `git branch -m` по замерам эпика #428 падал 11 раз на
`could not lock config file .git/config`: конфиг общий у всех worktree, его держит git другого чекаута; ссылка
переименована, секция ветки (upstream) — нет, а повтор старого имени уже не находит. Скрипт повторяет шаг, упавший на
блокировке, ~10 с; не дождался — строка с командой, которая доделает, а чужую блокировку не удаляет.

Начало задачи стоило медиану 30 ходов до первой правки, из них 11 — только флоу (#666): `project check`, `task show`
задачи и эпика, проверка параллельной работы, `task status --branch`, имя сессии, загрузка инструментов приложения по
одному — каждый ход на 170–190K контекста. `task start N --branch …` делает это одним вызовом: `project check` раз за
сессию (метка в `project-checks/<id сессии>`), задача — выводом `task show`, затем остановки до изменений, код 1:
открытые вопросы задачи или эпика — их задают первыми; открытый PR задачи или её ветка `*/N-*`, не текущая, — работа
идёт в другом месте. Дальше — `task status` со всем, что он делает, оценка, если её нет, и то, что нужно агенту дальше:
имя сессии, ветка, сценарии и в Claude Code одна строка `ToolSearch select:` со всеми инструментами приложения, что
флоу зовёт в задаче. Задание исполнителя (#709) берёт задачу тем же `task start --branch`, а не `task status`
отдельными ходами после вопросов и `task show`; перезапуск — `task start --resume`: ветка и PR прежнего исполнителя —
работа, которую продолжают, а не остановка, текущая ветка не переименовывается. Починка красного выпуска остаётся на
`task status --branch`: её новая ветка режется рядом с влитой веткой задачи, на которой `task start` остановился бы.

Хвост задачи — от `gh pr create` до конца — стоил медиану 18 ходов на 260–330K контекста, 22 % всех трат, ≈19 из них
— механика (#668): push, PR со `spec-diff` и `pr labels`, ожидание CI, `pr premerge`, мерж, ожидание деплоя,
`task actualize`, субагент, `task close`. `task finish N` — одна возобновляемая команда: каждый вызов делает, что готово
за его `--timeout`, и печатает состояние и следующий шаг, повтор продолжает с того же места — состояние читается с
GitHub и из git, плюс две метки в `finishes/` (деплой мержа прошёл, промпт актуализации напечатан — второго субагента
не будет). Мерж остаётся отдельным вызовом `gh pr merge <N> --rebase`: на него опирается правило разрешений владельца
в режиме auto. Коды — что делать дальше: 0 — готово, 1 — исправить (красный CI, конфликт, отказ push), 3 — красный
`main`, 4 — шаг агента (мерж, субагент актуализации), 5 — время вышло, тот же вызов снова. PR в ветку пачки CI не
ждёт, а после мержа в неё — ничего: остальное делает выпуск.
Задачу закрывает сам мерж — `Closes #N` в теле PR (#761), поэтому хвост завершён не по состоянию issue, а по тому, что
ставит `task close`: Status «Готово» и записанный факт; закрытая без PR или отменённая задача хвоста мержа не начинает.

Субагент актуализации сам собирал то, что скрипт знает (#435): в одном проекте 248 запусков, ~35 вызовов на запуск, 40%
из них — `gh`, почти половина ошибок — оболочка, а не смысл. Механику, где решать нечего, `task actualize` делает сам:
снимает blocked by на выполненных задачах (закрытых и на этой, чей PR влит), метку вопросов без открытых вопросов в
разделе, закрывает milestone задач эпика без открытых задач (milestone самой задачи и эпика — `task close`: задача может
быть ещё открыта), и пишет правки одной строкой в комментарии к эпику. Субагенту остаются проверки по смыслу — 1, 3 и
5. Тексты эпика и его открытых задач и файлы PR — в задании, а задание печатает `--assignment` первым вызовом субагента:
сессия на пиковом контексте переписывала бы десятки КБ в вызов субагента выходными токенами, ей достаются две строки
промпта. Копии связей в тексте и ответы на открытые вопросы в комментариях (`k. ✅ …`) задание называет, а не правит:
в строке бывает и смысл, а нумерация комментария — своя (ответы на концепцию, а не на раздел вопросов).

Проверка 5 («повторы → стандарт») после почти каждой закрытой задачи эпика заводила новую задачу на следующий дубль
рядом (#636): за день — семь задач по 0,5–1 ч на копии одного помощника, у каждой свой PR, CI, деплой и своя
актуализация, которая снова что-то находила. Причин две, и правки две. Повторы в файлах, которые задача и так правит,
исполнитель исправляет в том же PR, до мержа, — канон и задание `task queue --assignment` любого исполнителя; после
мержа дописать их в задачу уже нельзя. Повтор вне файлов задачи остаётся актуализации, но её находке сначала ищется
открытая задача эпика того же рода в Бэклоге — туда она идёт пунктом, а новая заводится, только когда такой нет или
задача уже идёт («В работе» или с открытым PR — её работа не ждёт новых пунктов). Род задачи — суждение субагента, а
статус — механика: задание пишет его под заголовком каждой открытой задачи, открытый PR ищется, как в очереди, — по
связи, ветке задачи и «Closes #N». Итог актуализации называет, куда ушла находка: «дописано в #N» или «заведена #M».

Задача — один PR, а доправка к влитому PR — та же задача: влитых PR у задачи бывает два, и GitHub связывает с ней
только тот, где «Closes #N». `task close` убирал одну ветку — ветку чекаута, а ветку первого PR оставлял и локально, и
на хостинге (#435). Ветки убираются у каждого влитого PR задачи — связанного и найденного, как несвязанный, по ветке и
«Closes #N». Ветка чекаута без влитого PR уходит, только если `git cherry` видит её в основной ветке: другой влитый PR
той же задачи невлитую работу влитой не делает.

`task close` убирает и окружение задачи: её стеки Docker Compose (скилл `task-env`, эпик #392) живут, пока их не снимут,
и держат тома и сети машины. Закрытие зовёт `task-env down <N>` в чекауте задачи и печатает его строки; ошибка снятия —
строка `!`, закрытие идёт дальше, оставшийся стек найдёт `task-env prune`. Каталог — не чекаут репозитория задачи —
не трогаются ни ветки, ни стеки: их имена — из `origin` чекаута. `--no-git` стеки снимает: флаг — про ветки. Скрипт
зовёт `gh` и Docker, а в песочнице Claude Code ни то ни другое не работает, и запись `excludedCommands` для скрипта
вызов из неё не выводит — `task close` идёт вне песочницы (#395).

Сессия-диспетчер берёт не задачу, а очередь — «сделай все задачи эпика», «поправь все баги High» (#471). Чипы
запускал владелец, каждый кликом; дочерние сессии приложения (`start_session`) тогда были закрыты серверным флагом, а фоновый
субагент в своём worktree запускается без клика и будит сессию ответом. `task queue` печатает готовые задачи —
открытые, не эпики, не в работе, без открытых блокеров — по `Priority`, затем по номеру, у каждой — промпт
исполнителя «Задача #N …»: по нему `est` привязывает работу субагента к задаче, а задание целиком (`--assignment`)
исполнитель печатает сам — диспетчер не копит его в контексте. Очередь читается заново после каждого ответа, так
подхватываются задачи, заведённые по ходу. Субагент делит id сессии с родителем: закрепление первой задачи отказало бы
второму исполнителю и отдало бы `est` всю сессию диспетчера как одну задачу, поэтому `task queue` помечает сессию
диспетчером (`dispatchers/<id сессии>` в каталоге конфигурации), и `task status` в ней не закрепляет. Фоновые
исполнители останавливаются с процессом приложения, как и ожидания, но их транскрипты целы, и приложение называет их в
уведомлении (#528). `task resume` велит диспетчеру продолжить каждого через `SendMessage` по id, а не запускать новых, и
называет команду очереди. В пилоте #471 перезапуск остановил трёх исполнителей с ветками задач в своих worktree и
незакоммиченными правками: новый получил бы свежий worktree, ветку задачи git ему не отдал бы, а работа осталась бы в
старом; продолженные сообщением, все трое довели задачи до мержа. Новый исполнитель — только если продолжить нельзя, и
задачу «В работе» он продолжает в worktree её ветки: строка о перезапуске в задании велит работать там (в Claude Code —
`EnterWorktree` с его путём), а не в своём.
Строка о перезапуске в задании — только для задачи «В работе» с веткой `*/N-*` в чекауте или на origin, с её именем:
печатаемая всем, она сбила исполнителя задачи из «Бэклога», и тот разбирал её в ответе (#511). Пишущих субагентов
исполнитель запускает по необходимости, без лимита (#516): лимит «не больше трёх» — на исполнителей, которых видит
диспетчер, а о своих субагентах задание молчало, и исполнитель гадал. Каждому — свой worktree и «Задача #N» в начале
промпта, иначе `est` не привяжет его работу; их worktree и ветки после мержа убирает исполнитель — он знает, что их
коммиты уже влиты, а по веткам этого не видно: cherry-pick и rebase-мерж меняют SHA.

В работе — строка `=` — не только «В работе» (#513). В пилоте #471 задача с открытым PR, пока исполнитель ждал CI, была
строкой ○ среди не готовых, а выданная, пока исполнитель не поставил «В работе» (он делает это после вопросов задачи),
оставалась среди готовых: очередь расходилась с тем, что идёт, и диспетчер считал работающих сам. Теперь `=` — и
открытый PR (со ссылкой), и выдача исполнителю этой сессии: `--assignment` в сессии (с #546 — в любой) дописывает задачу в
`dispatchers/<id сессии>.tasks` — отдельный файл, его дописывают исполнители параллельно, а маркер очередь
переписывает. Выдача живёт всю сессию: любой ответ исполнителя не делает задачу готовой — «влито» закрывает её,
«вопрос» ждёт владельца, «сломалось» не перезапускают, — и перезапуск приложения тоже: остановленного исполнителя
продолжают сообщением (#528). Прежде `task resume` выдачу снимал — исполнители считались мёртвыми, — и задача, которую
исполнитель ещё не взял «В работе», вернулась бы в готовые и ушла второму исполнителю рядом с продолженным.

Исполнители диспетчера зовут скрипты из клона машины — так их называет промпт `task queue`, — а клон за сессию никто не
обновляет: в конце пилота #471 он отставал от `origin/main` на 5 коммитов, исправления `est` и `pr premerge`, влитые
ранними исполнителями, поздние не получали, и факт #508 посчитал старый `est` — исполнитель переписывал его руками
(#517). Факт пишет `task close`, поэтому клон подтягивает он, перед `est`: клон — чекаут, в котором лежит `est`, и только
у задачи его же репозитория — в других проектах влитый PR скриптов машины не меняет. Только перемоткой (`pull
--ff-only`), на основной ветке и без правок отслеживаемых файлов: другая ветка или правка в клоне — чья-то работа, её
не трогают, а строка называет, почему факт посчитан кодом клона. Неотслеживаемые файлы не мешают: в клоне живут
worktree сессий, а перемотка, которая затёрла бы файл, откажет сама. Отвергнуто: подтягивать клон в каждом `task queue`
— `task close` исполнителя идёт до его ответа диспетчеру, и очередь читается уже после; звать скрипты из worktree
исполнителя — факт пишет `task close`, свежий клон нужен именно там, а путь скриптов в промпте не меняется.

Внешний блокер жил в тексте описания, и очередь его не видела (#512): в пилоте #471 исполнитель отказался от задачи,
ждущей релиза bun, за 44 с, а очередь до конца сессии — 16 вызовов — выдавала её первой среди готовых, и диспетчер
держал список «не перезапускать» в голове. Блокер — issue другого репозитория — та же связь blocked by: GitHub
связывает issue любого владельца, очередь уже не берёт задачу с открытым блокером, а строка `○` называет его с
репозиторием — один номер назвал бы задачу этого. Блокер не issue (релиз, PR, чужой трекер) GitHub связью не даёт —
метка «внешний блокер», а причина — в последнем комментарии «Внешний блокер: …»: метка — признак, который видят доска
и поиск, текст причины в ней не уместить. Блокер закрыт или метка снята — задача снова среди готовых. Актуализация
снимает blocked by только с закрытого внешнего блокера: номер влитой задачи у issue другого репозитория — совпадение.

Свой worktree исполнитель убрать не может — он в нём работает, а `task close` ставит его на `origin/main` и советовал
убрать его из основного чекаута (#515). В пилоте #471 каждый из 16 исполнителей кончал ответ этой просьбой, диспетчер
16 раз проверял `git status` и убирал worktree руками, ещё 4 с ветками `worktree-agent-*` оставили субагенты
исполнителя #439. Убирает следующий `task queue` диспетчера — он и так идёт после каждого ответа: worktree агентов
(`.claude/worktrees/agent-*`, как их заводит Claude Code) на `origin/main` или на ветке `worktree-agent-*`, чистые и без
коммитов вне `origin/main` — строкой `+` с веткой; с правками или невлитыми коммитами — остаются строкой `○` с причиной;
ветки `worktree-agent-*` без worktree — так же по коммитам. Влитое — по `git cherry`, по патчам: rebase-мерж меняет SHA,
а патч — нет; перенос с конфликтом меняет и патч — такая ветка остаётся строкой `○`. Свои субагенты исполнитель убирает
сам (#516), очередь подбирает, что осталось. Работающий агент не трогается: Claude Code блокирует его worktree (`git
worktree lock`, причина — `claude agent … (pid N …)`) и снимает блокировку, когда агент закончил; блокировка процесса,
которого нет (приложение перезапустилось), не держит. Worktree сессии и worktree агента на ветке задачи — задача не
закрыта — без строки: агент мог задать вопрос и ждёт ответа. `task close` в worktree агента вместо совета пишет `○`:
его уберёт очередь.

Блокировка не держит worktree исполнителя, которого диспетчер ещё продолжит через `SendMessage` (#533). Claude Code
снимает её, когда агент закончил ответ — любой, и «вопрос» тоже: в сессии-диспетчере задач #515–#533 worktree
исполнителя #528, запущенного после перезапуска, очередь убрала через 12 с после его ответа, а процесс приложения из
блокировки был жив. Продолженному
сообщением после перезапуска приложения блокировку не ставят: worktree исполнителей #515 и #518 после `task resume` шли
без неё. Исполнитель берёт задачу «В работе» и ветку задачи после вопросов, а до того его worktree чистый и на ветке
`worktree-agent-*` — очередь убрала бы его с веткой, и ответ владельца пришёл бы исполнителю без каталога. Поэтому
выдача помнит и worktree исполнителя: `--assignment` дописывает к задаче каталог, где его позвали, —
исполнитель зовёт задание первым, из своего worktree, — и очередь не трогает этот worktree, пока задача открыта. Задачу
закрыл исполнитель — worktree уходит, как прежде; задача вне очереди (`--epic` другого эпика) читается, только когда её
worktree подошёл к удалению.

Исполнитель отдавал ответ, пока его фоновые субагенты ещё работали (#565): исполнитель #545 ответил «сломалось: меня

Репозиторий переименовали — скрипт работает под нынешним именем (#560): имя из `--repo` или `origin` он первым
запросом сверяет с GitHub (`nameWithOwner`). На прежнее имя GitHub отвечает нынешним, и чтения по нему проходят, а
запись REST (`gh api -X …`) получает редирект 307, который `gh` для не-GET не повторяет: `task new --repo <прежнее
имя>` заводил задачу без оценки, а подсказки печатали прежнее имя, и команда по ним шла туда же. Клон, сделанный до
переименования, остаётся чекаутом репозитория: имя его `origin` сверяется так же.

`pr labels` упирался в предел GitHub — не больше 100 меток на issue (#569): одна мутация ставила задаче все решения
диффа, и PR, задевший почти все решения разом (смена раннера тестов переписывает тела всех тестов корня), падал целиком
— на задаче ни одной новой метки; у эпика объединение подзадач копится и упирается в предел раньше. Теперь место —
100 минус уже стоящие метки (все: первая страница в 20 меток прятала остальные). Помещается всё — ставится всё, как
раньше. Не помещается — метку получают решения, чьи утверждения PR меняет: `<папка>.md` или имена тестов из раздела
спеки тела PR (вывод spec-diff), по алфавиту, сколько помещается; правка только тел тестов и кода — строка `○` без
метки, что не поместилось — тоже `○`, код 0. Кодмод по всем тестам не меняет ни одного утверждения, а метка решения
значит «задача меняет решение». Отвергнуто: считать такую правку сквозной и не ставить ни одной метки — теряются и
решения, которые PR действительно меняет; выбирать по числу изменённых строк — кодмод с длинными телами вытеснил бы их.

Исполнитель закрыл задачу, пока его актуализация эпика ещё шла (#571): запустил её фоновым субагентом, не дождался,
позвал `task close` и ответил диспетчеру. Своего worktree у субагента актуализации нет — он работает в каталоге
исполнителя, — а следующий `task queue` счёл этот worktree затихшим (блокировки нет, HEAD на `origin/main`, правок нет)
и убрал: субагент остался без каталога, Bash отказывал в любой команде, правки к задачам эпика диспетчер применял
руками. Дыры две, закрыты обе. `task close` отказывает до изменений, пока в эпике есть открытые задачи, кроме этой, а
итога актуализации нет — комментария к эпику «Актуализация после #N, итог: …» на любом языке словаря: канон «после
обоих — `task close`» теперь проверяет скрипт. Итог субагент пишет всегда, «блок актуален» тоже: прежде без правок он не
писал ничего, и конец актуализации не был виден; комментарий механики скрипта пишется до субагента и итогом не
считается. Очередь не убирает worktree агента, в котором работает его субагент без своего worktree, — строка `○`
называет субагента: его видно по метаданным субагентов Claude Code (`parentAgentId` без своего `worktreePath`, на любую
глубину), а работает он, пока пишется его транскрипт — последние 15 минут. Тот же признак держит живым прежнего
исполнителя при перезапуске задачи. Отвергнуто: держать worktree, пока пишется транскрипт самого исполнителя, — он
пишется до самого ответа, и очередь после каждого ответа ещё 15 минут не убирала бы ничего.

Очередь — не единственный, кто убирает worktree (#628): у задачи без коммитов (правка данных инструментом проекта прямо в
базе, сверка, исследование) worktree исполнителя без изменений, и среда убирает его, как только исполнитель ответил, —
дважды подряд исполнитель запускал актуализацию фоновым субагентом, отвечал «ждёт субагентов», и через минуту Bash
субагента отказывал («working directory no longer exists»), итога на эпике не было, `task close` отказывал. Тот же
исход — когда диспетчер убирает worktree исполнителя сам, по чистому `git status`: живой субагент в нём из git не виден.
Поэтому задание исполнителя велит запускать субагента актуализации не в фоне и ждать его ответа в том же ходе, затем
`task close`, и только потом отвечать, а справочник диспетчера — убирать worktree исполнителей только `task queue`. Без
PR `task close` ждёт закрытой задачи, а исполнитель этого не знал и ждал: задание велит сначала закрыть issue как
выполненную с итоговым комментарием, а отказ `task close` по открытой задаче без единого PR называет ту же команду.
Отвергнуто: держать worktree, пока жив его субагент, средствами скрипта — worktree убирает среда, а не скрипт.

Облачную сессию приложение стартует с ветки из записи сессии, которая её запускает (`get_session` → `branch`), а не из
git (#588). Диспетчер эпиков #542 и #554 жил в worktree приложения на ветке `claude/<slug>-<hash>`, не запушенной, — все
пять облачных исполнителей упали на клонировании: «The requested branch or commit was not found». Снять ветку с
checkout (`git switch --detach origin/main`, как после `task close`) не помогло: запись сессии её помнит, и три
следующих упали так же, а перенести сессию в другой каталог приложение не даёт. У сессии в папке проекта без worktree
ветки в записи нет — её облачные сессии стартуют с `main`. Поэтому сессия, запущенная диспетчером, — в папке проекта:
своей ветки у неё нет, исполнители — субагенты и облачные сессии — стартуют с `main`. `task queue` в worktree
приложения (`.claude/worktrees/<имя>`, не `agent-*`) говорит об этом строкой `!` с папкой проекта и идёт дальше, код 0:
исполнители-субагенты ветвятся от `origin/main` в своих worktree, их это не задевает. Отвергнуто: ставить checkout
диспетчера на `origin/main` и удалять его ветку — облако берёт ветку не из checkout; пушить ветку сессии, равную
`origin/main`, — мусорная ветка на origin, и не проверено, что облако даёт каждой сессии свою.

Предел исполнителей — по месту исполнителя (#611): субагенты — до трёх сразу, облачные сессии — до пяти, число из
запроса владельца заменяет любой. «Не больше трёх» держит машину: субагенты делят её процессор, порты и очередь `slot`,
а та пускает две тяжёлые проверки. Облачный исполнитель идёт в своём контейнере и машину не нагружает — владелец решил
2026-10-17: облачных до пяти. Фраза о пределе одна во всех местах, где её читает диспетчер, — в каноне, в скилле
`github`, его справочнике и справочнике облачной сессии, — и проверка держит её во всех: предел, исправленный в одном
месте, расходился бы с остальными.

Задачу другого проекта диспетчер выдаёт сессией приложения (`start_session`) в папке проекта, в своём worktree:
субагент работает в worktree репозитория диспетчера (так шёл переезд четырёх проектов на тонкий флоу). Сессия-исполнитель
в режиме auto архивирует себя сама после «Всё сделано. Сессию можно закрывать.», но не всегда (#621): кончила вопросом
владельцу, а ответ ушёл диспетчеру; последний ход — ожидание деплоя, после которого строка до архивации не дошла.
Завершённые сессии оставались в списке, пока владелец не закрывал их руками. Владелец решил 2026-10-18: диспетчер
архивирует сам, если проект сессии в режиме auto (`"auto": true` в его `.agents/elves.json`); вне auto сессию закрывает
владелец, как и прежде. Задача закрыта — `task close` прошёл: PR влит, деплой зелёный, факт записан. Не архивируется
сессия с живой фоновой работой — приложение откажет («still has live work») — и сессия с вопросом владельцу без ответа:
архивная уходит из списка, и вопрос в её последнем ответе владелец не прочтёт. То же — облачному исполнителю, которого
диспетчер архивирует после своего `task close`. Правило — одной фразой в каноне, в скилле `github` и его справочнике, а
шаг называет последняя строка `task queue`: её диспетчер читает после каждого ответа исполнителя, а уведомление
приложения о конце хода сессии — такой же ответ. Как — `claude/CLAUDE.md`: `archive_session` с id сессии, отказ не
повторяют. Ради места в ядре канона (бюджет слов) из пункта о диспетчере в `AGENTS.md` ушёл вопрос исполнителя — он в
скилле `github`, — а исполнителей по видам называет скилл.

Промпт сессии-исполнителя приложения печатает `task queue --assignment N --session` (#624): прежде задание было только у
субагента — «Ты субагент, а не сессия»: сессию не называть, CI ждать обычным вызовом, последнюю строку не писать, — а
сессии всё это нужно наоборот, и при переезде четырёх проектов на тонкий флоу диспетчер писал её промпты руками. Зовёт
его сам диспетчер, как бриф облачного исполнителя: сессия ещё не запущена, её worktree приложение сделает позже.
Задание — сессия по канону своего проекта в его режиме (его печатает `check`): имя `#N <заголовок>`, CI и деплой —
фоновой командой, в конце — последняя строка канона и в режиме auto архивация; вопрос — в раздел вопросов и владельцу в
этой сессии; работа эпика задачи — `task new --epic` без своего исполнителя: её подхватит очередь диспетчера. `Next:` —
`start_session` с `cwd` — папкой проекта и `use_worktree`, промпт — строки до `Next:` как есть. Выдача записана у
диспетчера отметкой `@session` вместо worktree: очередь показывает задачу `=`, а не готовой. Отвергнуто: одно задание
на обоих с условными строками — субагент и сессия расходятся в половине пунктов, и каждый читал бы чужие.

Пачка диспетчера (эпик #645) уходит в `main` одним PR — `batch release` (#649): один полный прогон и один деплой на
пачку. Шаги выпуска руками — ребейз, `spec-diff`, `Closes` каждой задачи — теряют задачу: PR не в ветку по умолчанию
GitHub с задачей не связывает, а поиск среди последних PR видит 50. Поэтому задачи выпуска — все PR в ветку пачки
отдельным запросом: ветка задачи и «Closes #N» тела, как у PR задачи; не `Refs #N` коммитов, как предлагал текст
задачи, — PR и есть задача, а коммит может сослаться и на эпик. Ветка пачки ребейзится на свежий `origin/main` во
временном worktree — CI выпуска проверяет то, что ляжет в `main` после хотфиксов мимо пачки, а чекаут диспетчера не
трогается; конфликт — строка `!`, ветка как была, PR нет: его разрешает человек или виновная задача (#650). Последняя
строка `task queue` называет выпуск, когда все задачи в работе влиты в пачку: `=` такой задачи — не живой исполнитель.
Слово владельца «релизим» — та же команда при живых исполнителях, их не останавливают (вопрос 2 эпика): пока PR
выпуска открыт, очередь новых не запускает, а `pr premerge` не вливает PR в пачку — влитое сейчас изменило бы выпуск,
который проверил CI, и задача ушла бы в `main` без `Closes` и `task close`. После выпуска тот же `pr premerge` уводит
PR в следующую пачку диспетчера, без неё — в `main` с полным CI: исполнитель узнаёт это из шага, который делает перед
каждым мержем, а не из `SendMessage` диспетчера. Выпущенную ветку пачки с открытым PR в неё не удаляют ни `task
close`, ни очередь — удаление базы закрывает PR или уводит его в `main` мимо диспетчера; удаляет её очередь, когда PR
переведён. Следующую пачку после выпуска очередь заводит, только когда есть что раздать: закончивший диспетчер пустой
ветки пачки на origin не оставляет.

Стек задачи пачки снимал только `task close` — то есть выпуск (#765): за час диспетчера с тремя исполнителями на машине
стояло 12 стеков, 11 из них — отработавших, и полные прогоны живых исполнителей падали на таймауте подключения к
Postgres. Стек задачи нужен до мержа: после него задача ждёт только выпуска, полный прогон которого идёт в CI. Поэтому
задание исполнителя пачки называет `task-env down <N>` после мержа, до ответа диспетчеру, `task finish` PR, влитого в
пачку, снимает стеки сам, а `task queue` диспетчера — страховка: снимает стеки каждой задачи, влитой в пачку без
открытого PR (её исполнитель закончил), и печатает только `+` и `!` — уже снятый стек каждая очередь повторяла бы
строкой `○`. `task close` при выпуске снятых стеков не находит — строка `○`, закрытие идёт дальше.

В проекте без auto исполнитель диспетчера мержил PR задачи сам на зелёных проверках (#667): задание велело «как сессия

«да», пересланному диспетчером, — снова `pr premerge` (база могла уйти), мерж и шаги после него. Облачный исполнитель
диспетчеру не пишет — спрашивает владельца в своей сессии; сессия приложения и так работает в режиме своего проекта.
Очередь вне auto называет это ожидание в `Next:`, пока исполнители выданы, а шаги `batch release` — «да» владельца и
перед мержем выпуска: тот же мерж без подтверждения. В auto-проекте — как прежде. Отвергнуто: считать «да» на
диспетчера согласием на мержи эпика и говорить об этом владельцу до запуска — режим проекта тогда значил бы меньше, чем
одна фраза в чате.

Задача пачки вливается в неё сразу после проверок перед коммитом и `pr premerge` (#676, решение владельца после
пилота): исполнитель держал слот ещё на двух шагах — ожидании лёгкого CI на PR в пачку, который повторял те же
проверки в чистом окружении, и актуализации эпика после каждого мержа в пачку. PR в ветку пачки CI теперь не запускает
(шаблон `skills/spec/ci.md`, «Batches»), а актуализация — у выпуска: строка `Next:` после мержа PR выпуска — одна
команда `task actualize` со всеми задачами пачки, она группирует их по эпикам и печатает по субагенту на эпик. Задание
и отчёт называют задачи эпика из выпуска («Актуализация после #N, #M, итог: …»), выкаченное — их PR в пачку, а не PR
выпуска с файлами всей пачки; `task close` каждой принимает этот отчёт, а до него отказывает по эпику — называет задачи
эпика из выпуска и их `task actualize`. Задача без PR в пачку не идёт: её актуализация и `task close` — у исполнителя,
как вне пачки. Отвергнуто: актуализация на каждый мерж в пачку в фоне у диспетчера — то же число субагентов, а эпик
между мержами одной пачки не меняется.

Задача ведётся на языке проекта — `language` манифеста чекаута. Без манифеста `task new`, `task answer`, `task status`,
`task actualize` и `task close` отказывают кодом 2 до первого запроса (#681), как `project check` и `fix`: иначе задача
проекта на `ru` из свежего worktree без `.agents/` получала бы английские разделы, статусы и комментарии. Чтение —
`task show`, `task queue`, `task resume` — идёт: оно разбирает имена любого языка словаря; `task drop` имён не пишет.
Доска на другом языке, чем манифест (язык сменили без `fix`), — задача ведётся на языке доски, как прежде; прежде так
же молча шёл и вызов без манифеста.
